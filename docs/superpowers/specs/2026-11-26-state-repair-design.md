# 단위 테스트 피드백과 최신 상태 재구성 설계

상태: 2026-11-26 후속 요청에 따라 구현 완료. 실제 모델 실험은 시작하지 않았다. 구현·검증 기록은 ../reviews/2026-11-26-state-repair-implementation.md 참고.

## 사용자 확정 사항

- 대상은 `/home/kg/qus-domain-modeling`의 Qwen3-Coder-30B와 gpt-oss-20b이다.
- 코드 작성은 검증 실패를 돌려주고 수정을 요청하는 방식이다.
- 최초 코드 생성 이후 수정 요청은 최대 **30회**이다. 최초 생성은 30회에 포함하지 않는다.
- 완료 조건은 **현재 저장소에서 채점하는 단위 테스트 전체 통과**이다.
- modeling 파이프라인의 도메인 모델은 처음 생성한 것을 고정하고 코드만 수정한다.
- 대화 관리 규칙은 두 모델에 동일하게 적용하되 모델별 자원·샘플링 설정은 유지한다.
- 대화 전체를 누적하는 대신 **최신 상태로 입력을 재구성**한다.
- 사용자가 직접 실험을 시작한다. 다른 실험 종료 감시나 자동 실행을 추가하지 않는다.

## 설계 당시 코드와 변경 범위

`generate/generate.py:run_once`는 선택적 도메인 모델 생성 후 코드 생성 요청을 한 번 한다.
`eval/evaluate.py:evaluate_run`은 이후 별도로 임시 작업 폴더에서 단위 테스트를 평가한다.
`generate/run_batch.py`는 Qwen → gpt-oss, 각 모델에서 37 → 44 → 29 순서로 실행한다.
기본 파이프라인은 direct, 선택적으로 modeling/both를 지원하며 `--iters`는 독립 실험 수다.

이 변경은 생성과 평가 사이에 유한한 수정 루프를 연결한다. 입력·출력 계약과 현행 채점
항목을 사용하며, Minimal-CodeAgent/ADK 또는 자유로운 셸 도구를 도입하지 않는다.
이전 Minimal-CodeAgent 실험에서 사후 집계한 수정 구간과 새로운 수정 1회의 의미는 다르다.

현재 채점 범위는 37번 15개 지표/15개 명령, 44번 11개 지표/15개 명령,
29번 9개 지표/9개 명령이다. 37번의 2.3.2, 2.3.3 제외 규칙도 유지한다.
테스트 버전과 한계는 `benchmark/PROVENANCE.md`를 따른다. CLI 검증이나 공식 PRDBench
전체 점수는 이번 완료 조건에 추가하지 않는다.

## Approaches

1. 전체 대화 누적 + 모델 요약: 과거 추론과 도구 사용을 많이 남기지만, 요약 실패와
   모델별 대화 형식 차이가 추가된다. 이전에 설명한 대안이다.
2. 최신 상태 재구성: 사용자 선택. 원본 입력, 현재 코드, 최신 검증 결과를 매 요청에
   넣으며 동일한 관리 규칙을 적용하기 쉽다.

구현 제안은 기존 `LLM.chat(user_prompt)`를 재사용하는 것이다. 이미 매 요청이 단일 user
메시지이므로 다중 턴 메시지 API나 추론 이력 변환기를 새로 만들 필요가 없다.

## 수정 횟수와 종료 규칙

- `round=0`: 최초 코드 생성 및 검증. `round=1..30`: 실패 피드백을 받은 수정 요청.
- 완전한 통과가 확인되면 즉시 종료한다. 30번째 수정 결과가 통과해도 성공이다.
- 30번째 수정까지 미통과하면 `repair_limit`으로 종료한다. 31번째 수정은 없다.
- `--max-repairs` 기본값은 30, 0은 최초 생성만 검증하는 비교 조건이며 허용 범위는 0~30이다.
- 빈 응답, 잘린 응답, 잘못된 파일 형식, 동일 코드 재출력도 수정 응답을 받았다면 1회를
  소비한다. 이 경우 기존 코드와 마지막 유효한 검증 결과를 보존하고 원인을 피드백한다.
- API 연결/서버 오류의 기존 최대 5회 재시도는 같은 논리 요청 안에서 이뤄진다.
  수정 횟수와 별도로 기록하며, 실패를 숨긴 채 무한 재시도하지 않는다.
- 30회는 횟수 제한이며 전체 시간 제한이 아니다. 기존 API 응답 timeout=null 설정을
  유지하므로 요청 한 번이 오래 걸릴 수 있다. 별도 전체 개발 시간 상한은 추가하지 않는다.
- 반복 정체는 기록하고 알리되 별도의 조기 종료 횟수를 추가하지 않는다.
- 단위 테스트 timeout은 구현 실패 피드백이다. API 재시도 소진, 실제 평가기 장애,
  입력 무결성 위반, 필수 입력의 컨텍스트 초과, 사용자 중단은 별도 종료 사유다.
- 테스트 오류와 평가기 오류를 구별한다. 생성 코드의 import/수집 오류는 수정 대상이고,
  테스트 실행 프로세스를 시작할 수 없거나 평가 명세를 읽을 수 없는 경우는 실행 오류다.

종료 상태는 `passed`, `repair_limit`, `context_limit`, `modeling_error`, `api_error`,
`validation_error`, `integrity_error`, `interrupted`로 구분한다. `passed`는 평가된 코드의
해시가 현재 코드와 일치하고, 모든 채점 명령에 실제 통과 결과가 있을 때만 허용한다.
skip, 수집 0건, 오류, timeout, 비정상 프로세스 종료는 통과로 인정하지 않는다.

## 각 요청의 입력

고정 입력:
- 원본 PRD 전체, 인터페이스 계약 전체, 출력/수정 규칙.
- modeling이면 최초 생성한 도메인 모델 전체. direct에는 도메인 모델을 넣지 않는다.
- 제공 파일의 경로와 해시. 큰 제공 데이터(44번 subway_data.json)는 현재처럼 인터페이스의
  형식 설명을 사용하고, 매번 데이터 전체를 프롬프트에 붙이지 않는다.

변하는 입력:
- 현재 생성 코드의 전체 파일 내용. 삭제된 파일과 과거 버전은 현재 코드에 섞지 않는다.
- 최신 검증의 전체 지표 상태, 실패 명령, 실제 오류/traceback 발췌.
- 직전 출력 형식 오류가 있다면 그 내용. 코드 해시가 같은 재시도라면 그 사실.
- 최근 2회의 변경 파일·실패 항목·결과를 상세 기록하고, 더 오래된 회차는 프로그램이
  만든 한 줄 이력으로 제공한다. 과거 모델 설명이나 reasoning_content를 재사용하지 않는다.

기본 방식에는 별도 LLM 요약 호출이 없다. 요약 역할을 현재 코드와 구조화된 검증 상태가
맡는다. 동일한 순서·구성·축약 규칙을 두 모델에 적용한다.

## 컨텍스트와 모델 설정

- 실제 로드된 모델의 템플릿/토크나이저로 완성된 요청을 계산한다.
- 입력 예산은 현재처럼 `실제 context - 8192 - 1024`이다. 8192는 출력용 여유 공간이며
  생성 출력 상한을 8192로 바꾸는 것이 아니다. `max_tokens=-1`도 유지한다.
- 입력이 크면 오래된 한 줄 이력, 최근 상세 이력 순서로 줄인다. 다음으로 오류 본문을
  항목당 6000자 → 1500자 → 400자로 줄이되 모든 실패 ID/상태와 마지막 오류 줄은 남긴다.
- 원본 PRD, 인터페이스, 고정 도메인 모델, 현재 생성 코드는 임의로 잘라내지 않는다.
  축약 후에도 필수 정보가 안 들어가면 요청하지 않고 `context_limit`으로 기록한다.
- 매 HTTP 재시도 직전의 기존 런타임 검증도 유지한다. 다른 모델/설정으로 조용히 바꾸지 않는다.
- `generate/lmstudio_profiles.json`의 샘플링·추론·시드·CPU/GPU·캐시·컨텍스트 선택 정책은
  변경하지 않는다. 실제 로드된 값도 계속 기록한다.
- 현재 모델별 설정: Qwen temperature 0.7/top_p 0.8/top_k 20/repeat_penalty 1.05;
  gpt-oss temperature 1.0/top_p 1.0/top_k 0/repeat_penalty 1.0/reasoning_effort high.
  두 모델 모두 min_p 0, seed 42, API 재시도 최대 5회다.

## 파일 적용과 고정 입력

다음은 구현자가 제안하는 공통 기본 동작이다.

- 최초 생성은 기존 `<file path="src/...">전체 내용</file>` 계약을 사용한다.
- 수정 응답은 변경할 파일의 전체 내용만 보낸다. 나머지 파일은 보존한다.
- 불필요한 생성 파일은 `<delete path="src/..."/>`로 명시적으로 삭제할 수 있다.
  현재 실험에서 생성한 파일만 삭제할 수 있고 제공 파일은 삭제/수정할 수 없다.
- 전체 응답을 먼저 검사한다. 중복 경로, 갱신/삭제 충돌, 절대 경로, 상위 경로 이탈,
  심볼릭 링크 이탈, 제공 파일 덮어쓰기, 평가 파일 출력은 응답 전체를 거절한다.
- 잘린 응답의 일부 파일을 적용하지 않는다. 준비된 스냅샷에 모든 변경을 적용한 뒤
  완성된 코드 버전을 게시한다. 파일별 중간 상태를 다음 검증 대상으로 사용하지 않는다.
- PRD·인터페이스·도메인 모델·제공 데이터·테스트/평가 명세 해시를 저장한다.
  각 평가의 입력/테스트 복사본은 원본에서 새로 만들고 전후 무결성을 확인한다.
  변형이 발견되면 해당 점수를 무효로 처리한다. 원본 벤치마크는 자동 복구하거나 수정하지 않는다.
- 이는 실험 무결성 검사이며 악성 생성 코드에 대한 완전한 OS 격리의 보장을 뜻하지 않는다.

## 평가와 결과 보존

- 현재 `unit_test_items`의 명령 목록, 항목별 집계, 제외 항목, 명령당 60초 제한을 유지한다.
- 유효한 코드 변경을 적용할 때마다 채점 대상 전체를 평가한다. 일부 실패만 재검증해
  전체가 통과했다고 간주하지 않는다. 한 회차 내 명령 순서와 공유 작업 폴더 방식은 유지한다.
- JUnit 혼합 결과에 skipped가 있거나 프로세스가 비정상 종료했을 때 성공으로 오인하지
  않도록 성공 판정 테스트를 추가한다. 채점 항목/테스트 assertion을 바꾸는 변경은 아니다.
- 원문 stdout/stderr, JUnit, 명령/시간, 코드 해시를 회차별로 저장한다.
- 파일별 SHA-256을 경로 순으로 정렬해 정규 JSON으로 직렬화하고 그 SHA-256을
  `source_hash`로 사용한다. 개별 파일 해시는 `source_hashes`로 함께 보관한다.
- 최초·매회·최고·최종 점수를 구분한다. 최고 점수 동률이면 먼저 도달한 회차를 선택한다.
  최고 버전으로 자동 되돌리지 않고 최신 코드에서 다음 수정을 진행한다.
- 한 번도 유효한 평가를 하지 못했으면 점수는 null로 둔다. 실행 오류를 0점 관측값이나
  성공으로 꾸미지 않는다. 최신 코드에 대응하는 평가가 없으면 최종 점수 역시 null이다.
- 첫 입력부터 테스트 오류를 피드백하는 실험임을 기록한다. 이를 원샷 코드 생성 점수와
  섞지 않도록 initial/final을 별도 집계한다.

실험 단위는 `(model, project, PRD, pipeline, iteration)`이며 상태를 서로 공유하지 않는다.
modeling의 모델 생성은 실험 단위마다 한 번이다. 유효 JSON은 한 번 직렬화해 고정한다.
현재와 같이 완전한 비JSON 응답은 원문을 고정해 사용하고 `json_ok=false`를 기록하되,
빈/잘린 도메인 모델 응답은 `modeling_error`로 중단한다.

## 저장 구조와 배치 동작

기존 `output/<model>/<run>/<task>-<prd>-<pipeline>-iter-<n>/` 아래에 다음을 추가한다.

- `run.json`: 실험 식별자, phase/status, max_repairs, repairs_used, 입력 해시, 최초/최고/최종 참조.
- `rounds/000/`, `rounds/001/` ...: prompt.txt, response.txt, usage.json, record.json,
  코드 스냅샷, validation.json, 명령별 stdout/stderr/JUnit.
- 루트 `src/`는 최신 게시 코드, 루트 `result.json`은 그 코드의 유효한 최신 평가 결과다.
- 기존 `modeling.txt/json`, 최초 `codegen_response.txt`, 집계 `usage.json`도 유지한다.
  완료 여부는 usage.json 존재가 아니라 run.json의 상태로 판단한다.

`repair_limit`은 정상적으로 끝난 미통과 실험이므로 결과를 남기고 다음 작업으로 진행한다.
다른 오류/중단 상태는 현재처럼 배치를 중지하고 모델 정리를 수행한다.
`--iters`와 `--max-repairs`는 별개다. 기본 direct 실행은 6개 독립 실험이며 both는 12개다.
원시 로그·상태를 남기되 자동 재개는 이번 기본 기능에 추가하지 않는다. 중단된 기존 결과를
덮어쓰지 않으며, 다음 실행은 새 run-name을 사용한다. 명시적 체크포인트 재개는 후속 기능이다.

## 검증과 인수 조건

- 실제 모델 없이 가짜 응답 + 실제 작은 pytest 테스트로 실패→수정→통과를 재현한다.
- 최초 통과는 수정 0회, 마지막 허용 수정에서 통과 가능, 끝까지 실패 시 정확히 최초 1회+
  수정 30회의 논리 코드 요청 이후 종료하는 것을 검증한다.
- 원본 입력/모델 설정 불변, 모델/프로젝트/파이프라인/iteration 상태 분리,
  코드 퇴행·skip·형식 오류·API 오류·컨텍스트 초과·중단 시 잘못된 성공 표시 방지를 검증한다.
- 두 모델 실험을 실제 시작하는 일은 이 계획 문서 작성/구현 검증에 포함하지 않는다.
