# LM Studio CPU/GPU 배치 측정 — 2026-11-27

RTX 2070 SUPER 8 GiB, i9-10900K(물리 10코어/논리 20스레드), RAM 약 62 GiB인 현재
연구 서버에서 측정했다. SDK 2.1.0, CUDA llama.cpp 런타임 2.73.0을 사용했다.
이 결과는 **짧은 추론의 하드웨어 처리 속도**이며 PRDBench 전체 완료 시간이나 정확도 측정이 아니다.

## 반영한 설정

| 항목 | Qwen3-Coder-30B-A3B-Instruct | gpt-oss-20b |
|---|---|---|
| CPU expert 레이어 배치 비율 | 1.0 → **0.85** | 1.0 → **0.5** |
| 백엔드 시작 스레드 | 실제 7 → **10** | 실제 7 → **8** |
| 컨텍스트 | 32,768 유지 | 32,768 유지 |
| 양자화 | Q4_K_M 유지 | MXFP4 유지 |
| KV cache | F16, GPU, 양자화 비활성 유지 | 동일 |
| Flash Attention | 유지 | 유지 |
| 샘플링·추론 | temperature 0.7 등 기존 프로필 유지 | temperature 1.0, medium 등 기존 프로필 유지 |

기존에는 프로필·네이티브 추론 설정에 CPU 10이 기록되어 있었지만 서버는 `--threads 7`로
시작했다. 요청의 `cpuThreads=20`에서도 실제 CPU 작업 스레드 7개를 관찰했다.
네이티브 로드 설정 `llm.load.llama.cpuThreadPoolSize`를 넣는 시도도 이 백엔드에서는
적용되지 않았다. 이후 SDK의 공개 `llamaCppArgumentsOverride`로 기존 `--threads`만
교체하자 8/10/12/20이 실제 서버 인자에 반영되었다. 이번 실행기는 이 방식을 사용한다.
테스트에 사용한 모델 YAML 변경은 모두 원래 바이트 그대로 복원했다.

`llamaCppArgumentsOverride`는 실험적 SDK 기능이다. 다른 SDK/런타임에서는 지원 여부를
확인해야 한다. 네이티브 `prediction_config.cpuThreads`와 서버 시작 스레드 수는 별개로 기록된다.

## 측정 방법

- 다른 모델이 로드되어 있으면 거절하고, 배치와 같은 파일 잠금을 잡아 순차 실행했다.
- 각 측정마다 새 모델 인스턴스를 로드하고 종료 후 해당 인스턴스만 언로드했다.
- 모든 완료 측정의 입력 캐시 재사용 토큰은 **0**이었다. OS 파일 캐시까지 지우지는 않았다.
- 샘플링은 기존 프로필과 같고 seed는 42였다. gpt-oss 템플릿의 추론 강도는 medium으로 고정했다.
- SDK로 채팅 템플릿을 적용한 뒤 raw completion을 사용했다. 출력 상한에서 끊기는
  추론 응답의 파싱 실패가 하드웨어 비교를 방해하지 않게 한 것이다. 실제 실행기의 HTTP 경로는 별도로 점검했다.
- 탐색은 출력 384토큰, 확인 측정은 512토큰으로 고정했다. 전체 모델 응답을 끝까지 생성한 실험은 아니다.
- 최초 생성 입력은 현행 44번 vanilla PRD·인터페이스·생성 규칙으로 만들었다.
  수정 입력은 여기에 이전 실행의 코드 5개와 feedback level 1의 예시 점수(6/11)를 넣었다.
  이 점수는 입력 크기를 재현하기 위한 예시이며 새 테스트 성적이 아니다.
- 확인 측정은 입력별로 기존→후보→후보→기존 순서로 각각 2회 했다.
  같은 모델·입력의 템플릿 적용 후 SHA-256이 동일한지도 검사했다.
- VRAM은 `nvidia-smi`로 250ms 간격으로 측정했다. 표의 최대 사용량과 최소 여유는
  로드와 생성 중 관찰값이며, 샘플 사이의 순간 피크까지 보장하는 수치는 아니다.
- 입력 처리율은 입력 토큰 수 / 첫 토큰 대기 시간으로 계산한 근사값이다.
  출력 처리율은 백엔드가 보고한 `tokensPerSecond`를 사용했다.

PRDBench 점수를 보장하지 않는다. 전체 실험 시간은 생성 길이·수정 횟수·도메인 모델 생성에도
좌우되므로 측정한 속도 향상률을 전체 실행 시간에 그대로 적용하면 안 된다.
